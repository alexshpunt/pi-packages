# 코드 분리와 폴더 구조 규칙

코드는 **책임, 변경 이유, 상태·자원의 소유권**을 기준으로 나눈다. 저장소 전체에서 통일할 것은 이 경계와 의존 방향이며, 모든 패키지의 폴더 모양은 아니다.

이 문서는 `apps/`, `packages/`와 관련 지원 도구를 수정하는 유지보수자와 코딩 에이전트의 공통 작성 기준이다. 특정 실행 라이브러리나 의존성 주입 도구를 전제로 하지 않는다.

- 적용 대상은 신규 코드와 책임·의존성 경계를 바꾸는 수정이다. 단순 버그 수정에 무관한 파일 이동이나 전체 구조 개편을 끼워 넣어서는 안 된다.
- 기존 코드의 일괄 이관이나 준수 완료를 선언하는 문서가 아니다. 기존 `AGENTS.md`, 공개 API, 설치·배포 계약을 자동으로 대체하지 않는다.
- 기존 지침과 충돌하면 해당 계약을 우선 보존하고 차이를 명시해야 한다. 계약 변경이 필요한지는 별도로 판단한다.
- `~해야 한다`는 필수, `~해서는 안 된다`는 금지, `~하는 것을 권장한다`는 근거 있는 다른 선택을 허용하는 기본값, `~할 수 있다`는 선택 사항이다.

## 1. 먼저 적용할 기준

| 질문 | 기준 |
| --- | --- |
| 새 파일을 만들어야 하는가? | 별도의 변경 이유, 소유권, 외부 의존, 공개 계약 또는 로드 단위가 있는지 확인한다. |
| 새 폴더가 필요한가? | 같은 기능의 정책·상태·작업을 함께 찾기 어려워졌을 때 관련 파일을 묶는다. |
| 모든 앱에 같은 폴더를 만들어야 하는가? | 아니다. 평탄한 구조, 기능별 구조, 조립·기능·어댑터 구조를 필요에 따라 선택한다. |
| 타입을 따로 빼야 하는가? | 독립적으로 참조되는 계약을 드러낼 때 분리한다. 단일 구현 전용 타입은 가까이에 둔다. |
| 공용 패키지로 옮겨야 하는가? | 실제 독립 소비자와 같은 동작 계약을 확인한다. 모양이 비슷하다는 이유만으로 옮기지 않는다. |
| 상태를 어디에 두는가? | 그 상태의 유효성을 지키고 변경·교체·종료를 책임지는 기능에 둔다. |
| 새 구조가 더 나은지 어떻게 판단하는가? | 변경할 위치와 영향 범위가 분명해지고, 호출자가 내부 상태나 구현을 덜 알아야 한다. |

## 2. 함수·파일·폴더를 나누는 기준

### 분리를 검토해야 하는 경우

다음 중 하나가 실제로 나타나면 경계를 나눌 필요가 있는지 검토해야 한다. 조건이 있다는 이유만으로 파일을 기계적으로 생성하지는 않는다.

- 서로 다른 이유로 바뀌는 코드가 섞여 있다. 예를 들어 모델 선택 정책과 화면 표시 형식은 변경 이유가 다르다.
- 상태나 자원의 수명이 다르다. 요청이 끝나도 유지할 세션 상태를 요청 정리 코드와 구분해야 하는 경우다.
- 외부 SDK, 파일, 프로세스, 네트워크에 대한 지식을 한곳에 가둘 필요가 있다.
- 독립적으로 사용하거나 대체·검증해야 하는 계약이 있다.
- 여러 호출자가 같은 의미의 정책을 중복 구현하고 있다.
- 워커, CLI, 확장 진입점처럼 별도로 로드되거나 배포되는 단위다.

분리한 모듈은 맡는 책임을 한 문장으로 설명할 수 있어야 한다. 파일을 나눈 뒤에도 서로의 내부 필드를 직접 바꾸거나 계속 함께 수정해야 한다면, 경계를 잘못 나눈 것은 아닌지 다시 확인해야 한다.

### 함께 두어야 하는 경우

- 같은 불변조건을 지키며 항상 함께 바뀌는 작은 구현과 보조 함수는 가까이에 두는 것을 권장한다.
- 호출자가 하나인 helper는 기본적으로 호출자 곁에 둔다. 다만 독립적인 외부 연동이나 복잡한 알고리즘이라면 호출자가 하나여도 분리할 수 있다.
- 파일 길이, 함수 개수, 코드 중복 줄 수만으로 분리해서는 안 된다. 생성 데이터처럼 사람이 순서대로 읽지 않는 파일은 특히 별도로 판단해야 한다.
- 한 문장을 전달하는 함수, 같은 값을 다시 포장하는 타입, 이름만 바꿔 호출하는 계층을 형식 통일 목적으로 추가해서는 안 된다.

함수 추출은 작업의 의미를 드러낼 때, 파일 분리는 책임의 경계를 드러낼 때, 폴더 분리는 관련 파일의 소유 영역을 드러낼 때 사용한다.

## 3. 저장소 최상위 경계

| 위치 | 소유하는 것 | 두어서는 안 되는 것 |
| --- | --- | --- |
| `apps/<패키지>/` | 독립 설치되는 확장·제품의 기능과 통합 정책 | 다른 앱이 상대 경로로 가져다 쓰기 위한 숨은 공용 구현 |
| `packages/<패키지>/` | 명시적인 소비자를 가진 공용 라이브러리·설정·독립 배포 단위 | 특정 앱의 내부 상태를 역참조하는 구현 |
| 루트 `scripts/` | 여러 패키지에 적용되는 빌드·검증·릴리스 도구 | 설치된 앱이 실행 중에 필요로 하는 기능 구현 |
| 앱 내부 `scripts/`, `tools/`, `diag/`, `verification/` | 해당 앱의 개발·진단·검증 도구 | 운영 모듈의 숨은 의존성 |
| `docs/` | 저장소 공통 규칙과 여러 패키지에 걸친 문서 | 특정 앱에서만 유지할 상세 동작의 중복 명세 |

앱 하나에만 필요한 지원 도구는 그 앱 가까이에 두는 것을 권장한다. 실행 중 필요한 진단 기능은 개발용 진단 도구와 구분하고, 배포되는 소스 영역에 두어야 한다.

배포 번들은 구성 요소의 선택·버전·포함 파일을 소유한다. 구성 요소의 기능 정책을 번들에 중복 구현해서는 안 된다.

## 4. 폴더 구조는 필요한 만큼 선택한다

다음은 동등하게 허용되는 구조다. 규모가 커지면 반드시 다음 형태로 이관해야 한다는 뜻이 아니다. 기존 패키지에서 책임을 잘 드러내는 이름과 배치를 유지하는 것을 권장한다.

### 4.1 작은 패키지: 평탄한 구조

```text
src/
├── index.ts
├── config.ts
├── model-selection.ts
├── controller.ts
└── ui.ts
```

진입점과 소수의 책임 파일로 충분하면 하위 폴더를 만들지 않아도 된다. 위 파일명과 파일 개수는 예시이며 필수 세트가 아니다. 짧고 함께 바뀌는 설정 파싱·저장·타입은 하나의 `config.ts`에 둘 수 있다.

`index.ts`는 예시다. 실제 확장 진입점은 `package.json`의 `pi` 선언을, 일반 라이브러리의 공개 진입점은 `exports`·`main` 등 해당 패키지의 로딩 계약을 따라야 한다. 루트 `index.ts`를 쓰는 패키지를 이름 통일 때문에 `src/`로 옮겨서는 안 된다.

### 4.2 기능별 구조: 관련 코드를 함께 배치

```text
src/
├── index.ts
├── accounts/
│   ├── policy.ts
│   └── state.ts
├── models/
│   ├── catalog.ts
│   └── types.ts
├── cache/
│   ├── storage.ts
│   └── publication.ts
└── pi/
    ├── registration.ts
    └── commands.ts
```

정책·상태·작업을 기능별로 묶고, 호스트 연결은 `pi/`처럼 외부 대상을 드러내는 이름으로 구분할 수 있다. 기능 폴더를 `features/` 아래로 한 번 더 감싸야 할 의무는 없다.

### 4.3 조립과 외부 연동이 커진 구조

```text
src/
├── index.ts
├── app/
│   ├── composition.ts
│   └── requests.ts
├── features/
│   ├── accounts/
│   └── catalog/
└── adapters/
    ├── pi/
    ├── remote-api/
    └── storage/
```

| 영역 | 책임 | 맡지 않는 책임 |
| --- | --- | --- |
| 진입점 | 환경 확인, 구성 선택, 호스트에 등록 | 개별 기능의 복잡한 정책과 상태 전이 |
| `app/` | 구현 생성·연결, 여러 기능에 걸친 진입 흐름과 순서 | 모든 기능 상태를 직접 보관·수정하는 중앙 관리자 |
| `features/<기능>/` | 기능 정책, 공개 작업, 상태와 자원의 소유권 | 상위 조립부 역참조, 다른 기능의 내부 상태 변경 |
| `adapters/<외부대상>/` | 외부 호출, 프로토콜 변환, 저장, 호스트 반환 계약 | 기능 정책의 별도 사본 |

모든 기능에 `service.ts`, `types.ts`, `state.ts`, `index.ts`를 만들어서는 안 된다. 필요한 책임이 생긴 파일만 만들어야 한다.

`core/`는 여러 소비자가 공유하는 명확한 내부 기능 경계가 있을 때 선택할 수 있다. Pi와 CLI가 함께 쓰는 프로토콜 구현이 한 예다. 위치가 애매한 코드를 모으는 장소로 사용해서는 안 된다. `pi/`, `storage/` 같은 어댑터 폴더는 호스트가 하나여도 사용할 수 있다.

순수 라이브러리와 설정 패키지에는 위 앱 구조를 강제하지 않는다. `src/index.ts`와 의미 있는 기능 파일, 또는 배포할 설정 파일만으로 충분할 수 있다.

## 5. 의존성은 공개 계약을 따라 한 방향으로 연결한다

조립부는 구체 구현을 알아도 된다. 기능은 필요한 기능의 공개 계약만 알아야 한다. 들어오는 호출을 받는 어댑터는 기능을 호출하고, 기능이 외부에 요구하는 작업은 조립부가 연결한 의존성을 통해 수행하는 것을 권장한다.

다음 규칙을 지켜야 한다.

1. 기능에서 상위 진입점이나 조립 모듈을 다시 가져와서는 안 된다.
2. 기능 A가 기능 B를 사용할 때는 B가 외부 사용을 위해 제공한 작업·타입을 사용해야 한다. B의 내부 저장소, 변경 가능한 Map, 비공개 helper를 우회해서 사용해서는 안 된다.
3. 여러 기능을 연결하는 순서가 별도 책임이면 상위 흐름에 두어야 한다. 기능 하나의 완료·취소 정책까지 모두 상위 Coordinator로 올려서는 안 된다.
4. 전체 앱 객체나 모든 서비스를 모은 객체를 하위 모듈에 전달해서는 안 된다. 필요한 작업·값만 전달해야 한다.
5. 새 런타임 순환 의존을 만들어서는 안 된다. callback이나 이벤트로 모양만 감춘 채 서로의 상태를 변경하는 관계도 같은 문제로 취급해야 한다.
6. 타입만 참조하는 관계는 런타임 순환과 구분해야 한다. 정상적인 데이터 관계인지, 기능의 소유권이 서로 얽힌 것인지 검토해야 하며, 순환을 없애기 위해 무조건 전역 타입 파일로 옮겨서는 안 된다.
7. 앱 간 상대 경로 소스 import와 공용 패키지에서 앱 내부로 향하는 역의존을 만들어서는 안 된다. 패키지 간에는 선언된 의존성과 공개 진입점을 사용해야 한다.

기능의 공개면은 별도의 `index.ts` 없이 `catalog.ts`나 `service.ts`의 명시적인 export로 제공할 수 있다. 모든 TypeScript export를 패키지의 외부 공개 API로 간주할 필요는 없지만, 다른 기능에서 사용하도록 의도한 접점과 내부 구현은 구분해야 한다.

호스트·SDK의 공개 API를 우선 사용해야 한다. 불가피한 비공개 API 접근은 좁은 어댑터에 격리하고, 지원 범위·검사·실패 동작을 명시해야 한다. 어댑터에 격리했다는 이유만으로 비공개 API 사용이 정당화되지는 않는다.

## 6. 타입과 계약은 의미의 소유자 가까이에 둔다

| 종류 | 기본 위치 | 별도 파일로 나눌 조건 |
| --- | --- | --- |
| 구현 하나에서만 쓰는 타입 | 해당 구현 파일 | 독립적으로 참조할 계약이 생겼을 때 |
| 기능의 데이터와 공개 작업·결과 | 그 의미와 유효성을 소유하는 기능 | 여러 구현 파일이나 외부 소비자가 독립적으로 참조할 때 |
| 기능이 외부에 요구하는 좁은 의존 계약 | 소비 기능 가까이 | 외부 구현을 주입하거나 수명·실패 계약을 숨길 필요가 있을 때 |
| 외부 DTO·wire 형식 | 해당 프로토콜·어댑터 경계 | 여러 연동 파일이 같은 형식을 사용할 때 |
| 오류 클래스·스키마·상수·실행 식별자 | 해당 책임의 실행 모듈 | 다른 책임으로 분리할 실제 이유가 있을 때 |

제공 기능의 공개 계약과 소비 기능의 요구 계약을 구분해야 한다. 이미 맞는 공개 계약이 있다면 그대로 사용하거나 필요한 부분만 선택하고, 같은 의미의 인터페이스를 호출자마다 복제해서는 안 된다.

- 구현이 하나여도 외부 I/O, 수명, 안정적인 공개면, 테스트 대체 경계가 있으면 인터페이스를 둘 수 있다. 구현 개수만으로 도입 여부를 정해서는 안 된다.
- `types.ts`나 `contracts.ts`는 해당 기능의 계약을 분명히 드러낼 때 사용할 수 있다. 모든 기능의 타입을 저장소 또는 앱 최상위 파일 하나로 모으는 것은 피해야 한다.
- 타입만 사용하는 import에는 `import type`을 사용해야 한다. 실행 클래스·오류 생성자·스키마·상수까지 타입 전용 모듈에 숨겨서는 안 된다.
- 외부 DTO가 내부 정책을 지배하지 않도록 필요한 경계에서 변환해야 한다. 이미 의미가 같은 데이터를 이름만 바꿔 복사하는 DTO 계층은 강제하지 않는다.
- 공개 계약에는 구현을 감추는 데 필요한 입력·결과·오류·읽기 전용 범위를 명시해야 한다. 내부 helper까지 모든 반환 타입을 별도 이름으로 만들 필요는 없다.

## 7. 상태와 비동기 작업에는 소유자가 있어야 한다

상태 소유자는 생성·변경·무효화·교체·종료 중 필요한 작업을 책임져야 한다. 다른 모듈에는 상태를 직접 바꾸는 참조보다 공개 작업과 읽기 전용 결과를 제공하는 것을 권장한다. `readonly` 타입 선언만으로 실제 객체의 공유·변경이 통제된다고 간주해서는 안 된다.

조립부는 소유자를 만들고 연결한다. 작은 앱에서는 조립 함수 안의 클로저가 상태를 소유할 수 있지만, 모든 세션 상태를 조립부로 모으는 규칙으로 확대해서는 안 된다. UI 자체의 표시 상태와 기능의 업무 상태도 구분해야 한다. UI는 기능의 공개 작업을 통해 업무 상태를 변경해야 한다.

비동기 작업과 자원에는 다음 조건을 적용해야 한다.

- 작업을 시작할 때 누가 완료·실패·취소·정리를 책임지는지 정해야 한다. 호출 함수가 반환된 뒤에도 남는 작업은 특히 소유자를 명시해야 한다.
- 소유권을 인계했다면 현재 소유자가 정리해야 한다. 이전 소유자의 늦은 완료·취소·정리가 새 소유자의 상태를 바꾸어서는 안 된다.
- 호출자의 취소 신호와 옵션을 보존하고 최종 소비자까지 전달해야 한다. 내부 수명 신호를 추가하면서 호출자의 선택을 덮어써서는 안 된다.
- 요청·작업·세션·인스턴스·프로세스의 수명을 같은 단위로 취급해서는 안 된다. 어느 종료가 어느 자원을 닫는지는 해당 기능의 계약으로 정해야 한다.
- 이벤트 전달, 대기 해제, 결과 발행, 자원 종료의 순서를 보존해야 한다. 코드 분리를 이유로 동기 처리를 비동기 큐로 바꾸어서는 안 된다.
- 캐시는 범위, 무효화 주체, 종료 시 처리 방식을 소유 기능에서 정해야 한다. 캐시 도입이나 제한값 변경은 코드 분리와 별도의 동작 변경이다.

인스턴스나 세션에 속한 가변 상태를 모듈 전역에 두어서는 안 된다. 프로세스 공유 레지스트리처럼 계약상 필요한 전역 상태는 예외로 허용할 수 있다. 이 경우 키, 소유자, 등록·교체·재로딩 동작, 해제 범위와 해제 뒤에도 남는 것을 명시해야 한다.

## 8. 정책·외부 연동·오류 표현을 구분한다

선택, 판정, 계산처럼 입력으로 결과를 정할 수 있는 로직은 순수 함수로 작성하는 것을 권장한다. 외부 I/O와 시간·환경 조회는 그 경계를 드러내고 필요한 값이나 좁은 작업으로 전달하는 것을 권장한다. 이 구분이 항상 별도 폴더나 클래스 생성을 뜻하지는 않는다.

- 기능 정책은 무엇을 허용할지, 언제 재시도·복구할지, 어떤 상태를 유지할지 결정해야 한다.
- 외부 연동은 프로토콜의 입력·출력·오류를 해석하고, 정해진 정책을 외부 API에 맞게 실행해야 한다.
- 파일 저장의 원자적 쓰기·잠금·descriptor 해제는 저장 구현이 책임져야 한다. 무엇을 언제 저장할지는 소유 기능의 계약이다.
- 사용자 메시지, 호스트 반환 형식, CLI 종료 코드로의 변환은 해당 외부 경계에서 수행하는 것을 권장한다. 내부 오류를 여러 계층에서 중복 알림해서는 안 된다.
- 호스트가 핸들러 예외를 기록만 하고 원본 처리를 계속하는 경우, 어댑터는 예외를 잡아 해당 기능이 정한 보류·취소·중단 등의 안전 결과를 적용해야 한다. 단순히 다시 던지는 것으로 안전 처리가 완료되었다고 판단해서는 안 된다.

지속 상태의 불변조건이나 자원 수명을 보호할 때는 클래스 또는 클로저 기반 객체를 사용할 수 있다. 무상태 함수를 묶기 위한 `Manager`·`Service` 클래스나 모든 함수의 인터페이스를 추가해서는 안 된다. 함수와 클래스의 선택은 책임과 수명으로 판단해야 한다.

## 9. 공용화는 가장 좁은 범위부터 한다

공용화는 다음 순서로 검토하는 것을 권장한다.

1. 같은 기능 안에서 중복된 정책을 한곳에 둔다.
2. 같은 패키지의 여러 기능이 같은 계약을 쓰면 패키지 내부의 공통 책임으로 둔다.
3. 독립 패키지의 소비자들이 같은 계약을 쓰면 `packages/` 추출을 검토한다.

`shared/` 자체는 금지하지 않는다. `shared/http.ts`, `shared/concurrent.ts`처럼 책임이 드러나는 모듈은 허용할 수 있다. 반면 서로 무관한 함수·상수·타입을 `utils.ts`, `helpers.ts`, `common.ts`라는 이름 아래 계속 모아서는 안 된다. 특정 기능 안의 작은 공통 helper도 소유 영역과 역할이 명확해야 한다.

### 공용 패키지로 추출할 조건

앱의 중복 구현을 추출할 때는 실제 독립 소비자 둘 이상이 같은 의미·입력·결과·실패·수명 계약을 사용하는 것을 기본 근거로 삼는다. 독립 배포할 제품 자체를 만드는 경우에는 소비자 수가 필수 조건이 아니다.

다음 사항도 확인해야 한다.

- 앱 내부를 역참조하지 않고 계약을 설명할 수 있어야 한다.
- 앱별 조건 분기 대신 안정적인 공통 책임을 제공해야 한다. 서로 다른 동작을 강제로 합치기 위한 옵션이 늘어나면 추출 범위를 재검토해야 한다.
- 소유자, 버전·호환성·배포 관리 방식, 필요한 검증을 정해야 한다. 비공개 워크스페이스 설정 패키지에 공개 npm 릴리스를 강제하지 않는다.
- 실제 소비 환경이 공개 진입점과 배포 형식을 지원해야 한다. 빌드 산출물을 소비한다면 필요한 빌드 순서와 배포 포함 파일도 확인해야 한다.

공용 패키지가 반드시 호스트 독립적이거나 반드시 컴파일 산출물을 배포해야 하는 것은 아니다. 호스트 전용이라면 범위와 의존성을 명시해야 한다. 호스트가 제공하는 패키지는 루트 지침의 peer 의존성 규칙을 따라야 한다. `sideEffects: false`는 실제 부수 효과가 없을 때만 선언해야 한다.

## 10. 이름·공개 진입점·import 규칙

- 파일과 폴더 이름은 책임이나 외부 대상을 드러내야 한다. 기존 패키지의 명명 관례를 유지하고, 이름 통일만을 위한 일괄 변경은 하지 않아야 한다.
- `service.ts`, `controller.ts`, `state.ts`, `policy.ts`는 실제 역할이 그 이름과 맞을 때 사용해야 한다. 서로 다른 역할을 같은 이름으로 감추어서는 안 된다.
- 새 불리언 이름은 `is`, `has`, `can`, `should` 등으로 의도를 드러내고, 단위가 있는 수치는 `timeoutMs`, `sizeBytes`처럼 단위를 밝혀야 한다. 공개 식별자·wire 키는 내부 명명 규칙을 이유로 바꾸어서는 안 된다.
- 패키지와 의미 있는 하위 기능의 공개 진입점에서 재수출을 사용할 수 있다. 필요한 이름만 명시적으로 재수출하는 것을 권장한다.
- 신규 `export *`는 공개 범위를 자동으로 넓히므로 기본적으로 피하는 것을 권장한다. 기존 공개 재수출은 사용처를 확인하지 않고 제거해서는 안 된다.
- 내부 구현은 자신을 다시 내보내는 진입점 파일을 import해서는 안 된다. 필요한 내부 파일을 직접 참조해야 한다.
- 외부 소비자는 패키지가 선언한 공개 진입점을 사용해야 한다. 워크스페이스에서 접근 가능하다는 이유로 다른 패키지의 내부 소스 경로를 사용해서는 안 된다.

소스 배포 여부만 보고 `.ts` 또는 `.js` import를 일률 적용해서는 안 된다. 실제 실행 환경, `tsconfig.json`, 해당 패키지의 기존 관례를 따라야 한다. 진입점과 재수출을 바꾸면 기능 외에 공개 API와 로딩 계약도 함께 검토해야 한다.

## 11. 구조 변경은 배포와 기존 동작을 함께 보존한다

파일을 옮기거나 공개면을 바꿀 때는 호출자부터 최종 소비자까지 확인해야 한다. 특히 다음 연결을 놓쳐서는 안 된다.

- 운영 import와 타입 참조
- 테스트의 내부 경로 또는 `dist/` 참조
- `package.json`의 `pi`, `files`, `exports`, `main`, `types`
- 번들의 준비된 사본과 포함 목록
- 필요한 런타임 리소스, 생성 파일, 패키지 검사 목록

운영 코드가 테스트·개발 도구를 통해 필요한 구현이나 fixture를 가져오게 해서는 안 된다. 생성 파일은 직접 고치기보다 원본과 생성 경로를 변경해야 한다.

구조 변경에는 기존 기능의 오류·취소 의미, 저장 형식, 이벤트 순서, 동기 반환, 옵션 우선순위의 변경이 자동으로 포함되지 않는다. 새 재시도·시간 제한·동시 실행 정책도 별도 요구사항으로 다뤄야 한다.

검증은 해당 패키지의 지침과 기존 명령을 따라 변경 영향에 맞게 선택해야 한다. 타입 검사만으로 설치본 로딩이나 외부 서비스 동작을 입증했다고 보고해서는 안 된다. 단순 문서 변경 때문에 전체 빌드·테스트를 실행할 필요는 없다.

## 12. 적용과 예외 판단

허용된 폴더 구조 중 하나를 선택하거나 파일을 가까이에 유지하는 것은 예외 승인이 필요한 일이 아니다. 신규·변경 영역에서 이 문서의 판단 기준을 적용하되, 기존 코드가 다른 모양이라는 이유만으로 전체 이관을 시작해서는 안 된다.

구현자는 변경할 책임, 공개 계약, 상태·정리 소유자를 확인해야 한다. 검토자는 폴더 이름이나 파일 개수보다 다음을 확인해야 한다.

- 변경 위치와 영향 범위를 설명할 수 있는가?
- 새 계층이 실제 책임을 갖는가, 전달만 하는가?
- 다른 기능의 내부 상태에 대한 지식이 줄었는가?
- 타입·상수·오류·설정의 의미를 소유한 곳이 분명한가?
- 호출자의 옵션과 취소, 자원의 정리 책임이 최종 소비자까지 유지되는가?
- 공용화가 앱별 정책과 릴리스를 불필요하게 결합하지 않는가?
- 공개 API와 설치·배포 경계를 보존했는가?

필수·금지 규칙에서 벗어나야 한다면 이유, 영향 범위, 대안이 맞지 않는 이유를 해당 변경에서 명시하고 유지보수자의 판단을 받아야 한다. 이 문서의 선택 사항이나 이미 승인된 작업에 별도 승인 단계를 추가해서는 안 된다. 패키지 고유의 동작 계약은 해당 패키지 문서가 소유하며, 공통 규칙으로 몰아넣지 않는다.
